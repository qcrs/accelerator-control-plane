# 远端调用
* 远端 GPU 不是把 GPU 真正“搬到”客户端机器上，而是把客户端的 CUDA 调用通过网络转发到有 GPU 的服务器。

```
  GPU 节点上的业务容器                       GPU 服务器
  ──────────────────                       ──────────
  PyTorch / CUDA 程序
         │
         │  cudaMalloc、kernel launch、nvidia-smi……
         ▼
  远端 runtime client / shim
         │
         │  把函数名、参数、显存操作、返回值编码
         ▼
  网络：TCP / HTTP2 / RPC
         │
         ▼
                                        GPU Server
                                             │
                                             ▼
                                    真实 NVIDIA Driver
                                             │
                                             ▼
                                        真实物理 GPU
```

- 在客户端拦截 CUDA/NVML 调用；
- 维护远端的 CUDA context、显存地址、stream、event、句柄等状态；
- 把调用和数据通过网络传给服务器；
- 让服务器使用真实 GPU 执行。

# 怎么做

远端 runtime 只负责“调用能不能过去”，它不知道这张 GPU 是否已经被别人占用。因此平台一般还要有一层资源调度。

## 静态Endponit配置

远端 GPU Server A -> Endpoint A -> GPU 0
远端 GPU Server B -> Endpoint B -> GPU 0

平台提前把每台远端 GPU Server、地址、GPU 信息、runtime 类型写成配置。任务来了以后，控制器从这些 Endpoint 中选一个。

Cricket 很适合放在这类路线里：远端 server 静态运行，控制器选择一个预先登记的 endpoint，把 Cricket client 配置注入 Pod。

## 远端 GPU 池 + Controller 调度

远端 Server 上报：
- 有几张 GPU
- 每张卡型号、显存、健康状态
- 是否空闲
- runtime 版本
    │
    ▼
Controller 按容量、型号、策略选卡
    │
    ▼
创建租约 / 会话
    │
    ▼
注入远端 runtime

- 远端 GPU 是一个动态资源池，不只是静态 IP；
- 可以做型号筛选、显存筛选、容量统计、配额、故障隔离；
- 要有会话、租约、超时回收，避免两个人同时拿到同一张远端卡；
- 适合多台 GPU 服务器、多用户、多任务场景。

## 将远端 GPU 变成 Kubernetes 可声明资源

Pod / Job
     │
     ▼
  申请逻辑 GPU ResourceClaim
     │
     ▼
  DRA / CRD / Scheduler 选择：
    - 本地 GPU
    - 本地 MIG
    - 远端 GPU Endpoint
     │
     ▼
  根据绑定结果注入本地或远端 runtime

特点：

- 把远端 GPU 也纳入 Kubernetes 资源模型；
- 可以统一配额、属性筛选、审计和调度；
- 适合多个资源池、多团队、多种 GPU 类型；
- 实现复杂度最高；
- 仍然需要 Lupine、Juice、Cricket 这类 runtime 真正把 CUDA 调用送到远端。


## 仓库

### Lupine：更像“替代本地 CUDA Driver”

 Lupine 的思路比较直观：

  应用原来加载：
    libcuda.so.1
    libnvidia-ml.so.1

  远端模式加载：
    Lupine 提供的 libcuda.so.1
    Lupine 提供的 libnvidia-ml.so.1

  应用继续认为自己在调 CUDA，但实际加载的是 Lupine 的 shim。shim 再把调用用网络发给远端 server。

  它的特点：

  - CUDA/NVML 透明性较强；
  - 容器 client/server 路径清楚；
  - 可以暴露多个远端 server 的 GPU；
  - 代码、镜像、codegen 都比较完整；
  - 但“多个 server 的 GPU 在客户端可见”不等于“它已经替你调度好了”。

  最重要的一句汇报表述：

  > Lupine 解决的是“远端 GPU 怎么像本地 CUDA GPU 一样被应用调用”，不解决“哪张远端 GPU 应该分配给哪个任务”。

### Cricket：更像“传统 RPC 远端 CUDA 中间件”

  Cricket 的模式是：

  应用
    -> cricket-client.so
    -> RPC / rpcbind
    -> cricket-rpc-server
    -> 远端 GPU

  它的特点：

  - 通过 RPC 调用远端 CUDA；
  - 要处理 RPC 服务发现、端口可达性；
  - 应用的 CUDA 链接方式会影响是否能截获；
  - 适合运行环境和目标应用比较受控的场景。

  与 Lupine 相比，可以简单理解：

  - Lupine：更接近“用 shim 替换 CUDA/NVML 库”；
  - Cricket：更接近“通过 RPC 客户端库转发 CUDA 调用”。

### SCUDA：重点在“自动生成 API 包装”

  CUDA API 很多，手写每个函数的 RPC 转发很难维护。SCUDA 的思路是：

  读取 CUDA / cuBLAS / cuDNN / NVML 头文件
          │
          ▼
  自动生成 client RPC wrapper
  自动生成 server RPC wrapper

  它的主要价值是帮助理解：

  > 当 CUDA 新增 API 时，远端 runtime 如何扩展支持，而不是人工逐个写网络代理。

  但它是 Lupine 技术路线附近的 fork，更适合作为 codegen 和 API 覆盖研究参考，不一定要和 Lupine 同时采用。

  ### mrCUDA：不是普通“远端调用”，而是“运行中迁移”

  mrCUDA 讨论的是：

  任务先在远端 GPU 上运行
         │
  本地 GPU 后来空闲
         │
  尝试把正在运行的 CUDA 任务迁回本地

  这比启动前选择困难得多，因为必须处理：

  - CUDA context；
  - 显存内容；
  - stream、event；
  - 各种库句柄；
  - 多线程状态；
  - 可能还有多卡通信状态。

  因此它不应和 Lupine/Juice/Cricket 放在同一层理解：

  - Lupine/Juice/Cricket：任务启动前已经决定远端，然后远端执行；
  - mrCUDA：任务已经运行后，尝试改变执行位置。

  ———cricket-client.so 是客户端的 CUDA 拦截和 RPC 转发库；它让业务程序“看起来在用本地 GPU”，实际上在使用远端 GPU。

  ```
  Kubernetes Pod
   └── 业务应用：PyTorch / CUDA
          │
          │ cudaMalloc / kernel launch
          ▼
     client shim / client library
     ├── Lupine: libcuda / NVML shim
     ├── Juice: Juice client
     ├── Cricket: cricket-client.so
     └── SCUDA: libscuda
          │
          │ 把 CUDA 调用变成远程请求
          ▼
     高层通信方式
     ├── Cricket: RPC + rpcbind
     ├── Lupine: HTTP/2 风格通信
     ├── Juice: 自身 client/server 协议
     └── SCUDA: 生成的 RPC wrapper
          │
          ▼
     TCP/IP 网络
          │
          ▼
  远端 GPU Server
          │
          ▼
  真实 NVIDIA Driver + 真实 GPU
  ```
  远端 GPU 方案通常由“客户端 CUDA 兼容层”和“网络调用层”组成：客户端通过 shim、预加载库或 client library 截获 CUDA 调用，再通过 RPC、HTTP/2 或项
  > 目自定义协议，经 TCP/IP 网络发送到远端 GPU Server。Lupine、Juice、Cricket、SCUDA 的差异主要在客户端拦截方式和通信协议；它们都需要配合控制器、
  > 资源目录和租约机制，才能形成可调度、可分配的远端 GPU 资源池。
