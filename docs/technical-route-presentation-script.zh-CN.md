# 本地与远端 GPU 透明调用技术路线


---

## 一、正式演讲稿

### 0. 开场

各位好，今天我汇报的主题是“本地与远端 GPU 透明调用的技术路线”。

我们希望实现这样一种使用方式：业务提交任务时，只描述需要多少 GPU、什么型号、多少显存，以及是否允许共享。至于最终使用当前节点的 GPU，还是使用远端资源池里的 GPU，由平台在任务启动前决定。

整个问题可以拆成三部分。

第一部分是本地 GPU 管理，包括设备发现、整卡分配、切分共享和任务调度。

第二部分是远端 GPU 调用，也就是把业务发出的 CUDA 和 NVML 请求，通过网络发送到远端 GPU。

第三部分是平台控制层。它负责比较本地与远端资源，完成资源预留，再生成对应的容器运行环境。

CUDA 的全称是 **Compute Unified Device Architecture，统一计算设备架构**。NVML 是 **NVIDIA Management Library，NVIDIA GPU 管理库**。后面提到的 GPU-over-IP，可以直接理解为“通过 IP 网络使用远端 GPU”。


**本地组件负责分配 GPU，远端运行组件负责传递 CUDA 调用，平台控制层负责选择路径并把任务真正运行起来。**

下面先介绍两个运行场景

### 1. 技术路线全貌

#### 1.1 两个运行场景——对应原文 2.1

先看第一个场景：工作负载所在节点没有可用的本地 GPU。

业务程序仍然调用 CUDA。容器里的客户端接口适配库会接住这些调用，把函数参数、显存操作和返回结果转换成可以通过网络传输的请求。远端 GPU 服务端收到请求后，再调用真实的 NVIDIA 驱动和 GPU。

第二个场景：工作负载所在节点或者集群内存在可用 GPU。

平台把任务调度到 GPU 节点，容器获得对应的设备文件和驱动库，CUDA 调用直接进入本机驱动。网络转发环节在这条路径中不存在，因此它通常具有更好的兼容性和更低的调用延迟。

两个场景可以使用同一份业务代码，差别位于容器运行环境。

本地模式需要申请 Kubernetes 中的 GPU 资源，并获得本地设备访问权限。

远端模式需要装入客户端接口适配库，同时获得远端资源地址、会话凭据和网络访问权限。

因此，完整方案里实际存在三条相互配合的技术链路。

第一条是本地 GPU 路径，核心包括 NVIDIA 驱动、容器运行时、设备插件、GPU 切分以及 Kubernetes 调度。

第二条是远端 GPU 路径，核心包括 CUDA/NVML 接口拦截、参数和显存操作编码、远程过程调用、远端 GPU 服务端以及网络连接。

第三条是启动前选择路径，核心是比较资源、确定本地或远端模式、预留设备，并让本次运行保持在已经绑定的路径上。

#### 1.2 整体分支流程——对应原文 2.2

整体流程是这样子的


工作负载提交后，平台先读取逻辑 GPU 请求。例如，任务需要一张 GPU、至少 24GB 显存，并且允许在本地不足时回退到远端。

平台首先查询本地候选。查询内容包括节点上的 GPU 型号、空闲显存、整卡或切分状态，以及调度队列。

如果本地资源满足要求，平台先预留本地 GPU，再生成本地模式的容器配置。

如果本地资源不足，或者策略明确要求使用远端，平台会查询远端资源目录，选择一个合适的远端 GPU 资源端点。


平台选中端点以后，需要先做资源预留。资源预留成功，才能把客户端适配库、端点地址和凭据放进容器。

这里的顺序是“先选择并预留，后创建业务容器”。这样可以避免两个并发任务同时看到同一张远端 GPU 空闲，并且都尝试使用它。

#### 1.3 统一的工作负载流转——对应原文 2.3

可以分成六个步骤。

第一个步骤是提交请求。

本地和远端都使用同一种逻辑 GPU 需求。业务描述数量、型号、显存、切分方式和路径偏好，不直接填写远端服务器地址。

这里需要设计一套清晰的策略字段。例如：

- `LocalFirst`，本地优先，本地不足时允许远端；
- `RemoteFirst`，远端优先；
- `LocalOnly`，只允许本地；
- `RemoteOnly`，只允许远端。

实际字段可以使用代码中的英文枚举，但在汇报时直接说成本地优先、远端优先、仅本地和仅远端。

第二个步骤是查询候选。

本地侧查询节点设备、HAMi 软件切分份额和调度队列。

远端侧查询 GPU 主机、设备型号、可用会话。

平台先做硬条件过滤，再进行评分。硬条件包括显存、访问权限；评分因素可以包括排队时间、网络延迟、数据位置和使用成本。

第三个步骤是绑定资源。

本地模式由 NVIDIA 设备插件或 HAMi 分配具体 GPU。

远端模式由平台控制器建立资源预留、运行会话和租约。资源预留表示这张 GPU 已经被当前任务锁定；会话表示任务与远端服务端之间的一次运行关系；租约带有有效期，可以在任务异常消失后触发回收。

第四个步骤是准备运行环境。

本地容器会获得 设备文件、NVIDIA 驱动库和可见设备信息。

远端容器会获得客户端接口适配库、远端资源端点、认证材料和环境变量。业务原来的启动命令保持不变。

第五个步骤是调用 GPU。

本地模式下，CUDA 进入本机 NVIDIA 驱动。

远端模式下，CUDA 和 NVML 调用先进入客户端接口适配库，随后经网络到达远端 GPU 服务端。

这一阶段要关注远端运行组件覆盖了哪些 CUDA 接口、怎样处理显存指针和异步调用，以及是否支持目标框架和多 GPU 语义。

第六个步骤是结束与释放。

本地模式由 Kubernetes 节点管理进程和设备插件释放设备。Kubernetes 节点管理进程的程序名是 `kubelet`，演讲时说“节点管理进程”即可。

远端模式由客户端、服务端和平台控制器共同结束会话并回收 GPU。正常结束、容器崩溃、节点失联和重复清理，都要进入同一套回收流程。

一套完整流程最终要回答六个问题：

请求怎样表达路径偏好；本地卡和远端端点怎样比较；资源怎样防止重复分配；运行环境怎样自动注入；目标 CUDA 应用是否兼容；异常结束后资源怎样可靠回收。

有了这个全貌，下面再看每一段分别由哪些开源组件实现。

### 2. 本地 GPU 路线

#### 2.1 NVIDIA GPU 运维控制器和设备插件

本地整卡路径建议采用 NVIDIA GPU 运维控制器和 NVIDIA 设备插件。

GPU 运维控制器它负责管理 GPU 节点的基础软件，


NVIDIA 设备插件以每个 GPU 节点一个常驻实例的方式运行，主要做三件事：

第一，发现节点上的 GPU；

第二，把 GPU 数量和健康状态上报给 Kubernetes；

第三，在任务启动时把具体设备分配给容器。


Kubernetes 调度器看到请求后，会寻找有空闲 GPU 的节点。任务被放到目标节点后，NVIDIA 设备插件再把设备访问权限交给容器。

GPU 运维控制器负责把节点准备好，NVIDIA 设备插件负责把卡分给任务。这套组合适合作为本地整卡路径的基础。

#### 2.2 HAMi：本地共享、软件切分和 MIG

一张 GPU 只服务一个任务时，整卡分配最简单。如果任务显存使用较少，整卡独占会产生空闲空间，这时可以引入 HAMi。

HAMi 会把显存、算力份额和切分类型带入调度过程，并在容器运行时落实对应限制。

本地 GPU 可以表现为三种资源形态。

第一种是整卡。一个任务独占一张物理 GPU，隔离和计量最清楚。

第二种是 MIG 实例。MIG 是 NVIDIA 的多实例 GPU 技术，它在支持的 GPU 上划分固定规格的硬件实例。每个实例拥有相对独立的显存和计算资源。

第三种是软件切分份额。多个任务共享一张物理 GPU，HAMi 通过软件限制显存、算力或使用时间。

这三种资源在申请时都和 GPU 有关，但使用体验并不相同。平台需要记录切分类型、显存大小、算力份额和隔离等级，才能判断一份本地共享资源是否真的满足任务要求。

HAMi 解决的是本地 GPU 的共享和切分。远端 CUDA 调用仍然由后面介绍的远端运行组件负责。

#### 2.3 Volcano 和 KAI：队列、批任务与公平调度

训练、HPC 和多团队共享场景还会遇到排队和公平性问题。HPC 是高性能计算。

例如，一个分布式训练任务需要 8 个工作负载单元同时运行。如果只启动其中 3 个，已经占用的 GPU 也很难产生有效训练结果。

Volcano 提供批任务调度、队列和成组调度。成组调度的含义是：一组任务在资源足够时一起启动，资源不足时统一等待。

KAI 调度器更偏向 AI 工作负载，提供队列层级、资源预留、公平性和拓扑感知。拓扑感知指的是调度时考虑 GPU 之间的物理连接关系，让通信频繁的任务尽量使用距离更近的设备。

本地路线可以按需求逐层建设：

GPU 运维控制器和设备插件提供整卡基础；

HAMi 提供共享与切分；

Volcano 或 KAI 提供队列和调度治理。

### 3. 远端 GPU 调用路线

#### 3.1 远端调用是怎样发生的

远端调用可以分成五步理解。

第一，业务或者 PyTorch 发出 CUDA 调用。

第二，Linux 动态链接器把调用交给客户端接口适配库。

第三，适配库把函数名、参数、显存操作和会话信息编码成网络请求。

第四，远端 GPU 服务端收到请求，调用真实 NVIDIA 驱动。

第五，执行结果再沿网络返回给业务进程。

远端调用真正复杂的地方在于 CUDA 接口的数量和状态。

一个模型可能会使用：

- CUDA 驱动接口和运行时接口；
- 显存分配、释放与复制；
- GPU 计算核函数，也就是 Kernel；
- CUDA 执行流，也就是 Stream；
- 同步事件，也就是 Event；
- cuBLAS 矩阵计算库；
- cuDNN 深度学习加速库；
- 自定义 CUDA 算子；
- 多线程和多 GPU 通信。

所以，`nvidia-smi` 能够运行只代表部分 NVML 查询成功。目标 PyTorch、vLLM 或自定义 CUDA 应用是否可用，需要执行完整业务测试。

#### 3.2 Lupine

Lupine 是本次调研中适合优先验证的远端方案。

从技术结构看，它分成客户端和服务端两部分。

客户端提供 CUDA 驱动接口库和 NVML 管理接口库的替代实现。应用调用 CUDA 时，先进入这些替代库；替代库把函数编号、参数、显存操作和会话信息封装成远程请求。

远端 GPU 主机运行 Lupine 服务端。服务端收到请求后，调用本机真实的 NVIDIA 驱动，再把执行结果返回给客户端。两端主要通过 HTTP/2 等网络协议通信。

公开仓库包含客户端、服务端、代码生成工具、容器构建文件、测试和版本化镜像，便于固定版本进行复现。

代码生成工具会读取 CUDA、cuBLAS、cuDNN 和 NVML 头文件，自动生成一部分远程调用包装代码。这样可以减少手工编写大量接口适配函数的工作。

Lupine 的优势主要有三点。

第一，公开链路比较完整。从替代库、服务端到构建文件和测试都能在仓库中找到，适合搭建可重复的验证环境。

第二，容器接入方式比较直接。可以使用项目提供的客户端镜像，也可以通过动态库路径把接口适配库放进现有业务容器，业务启动命令通常无需改成远程调用命令。

第三，代码生成机制便于扩展接口。CUDA 或相关库增加函数时，可以先通过代码生成补出调用框架，再对指针、异步执行和回调等复杂语义进行人工验证。

它的局限也比较明确。

代码生成解决的是函数包装，函数背后的完整语义仍要测试。例如显存指针生命周期、CUDA 执行流、异步返回、多线程上下文和自定义算子，都可能带来兼容性问题。

Lupine 可以让一个客户端配置多台服务端，并把远端 GPU 按顺序显示成多个设备。跨服务端的设备间复制需要单独测试；部分数据可能经过客户端中转，性能与本机多卡环境会有明显差异。

另外，Lupine 重点解决 CUDA 和 NVML 的远端调用。远端 GPU 的资源目录、任务排队、独占分配、运行会话、租约、租户权限和审计，需要由平台控制层补充。传输加密可以放在 TLS 代理之后，身份认证和多租户授权仍要单独设计。

综合来看，Lupine 的优点是调用链公开、容器化程度较高、容易复现；主要风险是应用兼容性、跨服务端性能和平台管理能力还需要验证或补齐。因此，它适合作为 Linux 容器环境下的第一条概念验证路线。

#### 3.3 Juice

Juice 社区版也采用客户端和服务端结构。

客户端运行在使用 GPU 的业务侧，服务端运行在有物理 GPU 的机器上。客户端接住应用的 GPU 调用，再通过普通 TCP/IP 网络发送给服务端。公开材料覆盖物理机、虚拟机和容器，并提到 Linux 与 Windows 的组合。

Juice 的优势是部署形态相对完整。除了远端调用链，它的社区仓库还提供命令行工具、控制组件和 Kubernetes 部署配置等内容，适合参考一个 GPU-over-IP 方案怎样组织安装、服务端管理和跨环境部署。

跨平台也是它比较有辨识度的特点。如果实际环境同时存在 Linux、Windows、虚拟机和容器，Juice 的参考价值会高于只覆盖 Linux 动态库拦截的方案。

需要关注的第一点是版本适配。采用时要固定具体客户端和服务端版本，再用目标 CUDA、NVIDIA 驱动和框架镜像重新测试，不能根据“应用无需修改”的描述直接推断所有程序都兼容。

第二点是开源合规。除了 MIT 许可证，还要同时检查仓库附加条款、第三方依赖以及最终镜像里包含的软件。

第三点是资源控制。Juice 提供远端调用和部署管理的基础，但本地与远端的统一选择、跨任务的资源预留、租约一致性和平台审计仍然需要外部控制层。

综合来看，Juice 的优点是跨平台、部署形态较完整；主要风险是版本兼容性、附加条款和应用支持范围需要重新核实。它适合混合操作系统、虚拟机和容器场景，也适合作为 Lupine 的产品化对照。

#### 3.4 Cricket

Cricket 采用传统的远程过程调用路线。

客户端通过 `cricket-client.so` 文件拦截 CUDA 调用。这个文件可以直接讲成“Cricket 客户端动态库”。它接住动态链接的 CUDA 函数，再把请求发送给远端的 Cricket 服务。

服务端通过远程过程调用服务号和版本识别接口，部署时通常还会涉及 `rpcbind`。`rpcbind` 可以理解为远程调用服务登记和发现组件，它帮助客户端找到具体服务端口。

Cricket 的优势是结构清楚：客户端动态库负责拦截，远端服务负责执行，中间使用传统远程调用协议。对于接口范围固定、应用构建方式可控的程序，定位问题和修改接口都比较直接。

它的主要限制来自动态链接。目标程序需要实际经过 Cricket 能够拦截的 CUDA 动态库路径；如果框架把某些库静态链接进程序、使用了特殊封装，或者依赖尚未覆盖的接口，就可能绕过客户端动态库。

部署到 Kubernetes 时，还要处理服务发现、`rpcbind`、端口稳定性和网络访问。通用 TLS、身份认证和租户授权也需要额外建设。

综合来看，Cricket 的优点是远程调用结构直接、适合受控环境；主要风险是动态链接依赖、框架兼容性和 Kubernetes 网络配置。它适合目标程序构建方式固定、CUDA 接口范围明确的场景，也可以作为 Lupine 的传统远程调用对照。

#### 3.5 SCUDA、mrCUDA 和 TensorFusion

SCUDA 与 Lupine 属于相近的技术路线，而且是从 Lupine 分支出来的项目。

它会读取 CUDA、cuBLAS、cuDNN 和 NVML 头文件，生成客户端和服务端包装代码，再通过动态库预加载机制接管应用调用。

它的优势是代码生成思路清楚，适合研究怎样扩展 CUDA 接口，或者怎样为特定版本定制远程调用库。局限是它与 Lupine 的功能重合度较高，同时也不提供调度、资源预留、安全认证和租约管理。

因此，SCUDA 更适合作为代码实现参考。生产验证路线通常在它和 Lupine 之间选择一个主线，避免维护两套接近的客户端和服务端。

mrCUDA 研究的是远端执行向本地执行迁移。它建立在 rCUDA 之上，希望在本地 GPU 重新可用时，把任务从远端执行切换到本地执行。

它的价值是把运行中迁移涉及的状态问题具体化，包括 CUDA 上下文、显存内容、执行流、同步事件和函数句柄。局限是依赖环境较旧，同时采用 GPL-3.0 许可证，与现代 CUDA、PyTorch 和 Kubernetes 环境存在较大距离。

因此，mrCUDA 适合用于论文研究、状态迁移分析和实验设计，不适合作为当前远端调用平台的直接工程基础。

TensorFusion 属于一体化平台路线。它公开的方向同时覆盖 GPU 虚拟化、分数 GPU、远端 GPU 共享、资源池、调度、动态资源分配和监控。

它的优势是统一程度高。如果各个模块成熟并满足需求，平台可以减少自行拼接设备插件、远端运行组件和控制器的工作，并对外提供更一致的资源接口。

需要重点确认的是公开实现范围。项目说明中提到的在线迁移、GPU 上下文快照与恢复、企业级高可用和安全能力，可能分布在不同版本或企业功能中。评估时要逐个检查源码、部署配置、文档和许可证。

综合来看，TensorFusion 适合研究完整 GPU 平台应该有哪些对象和组件；是否直接采用，要经过模块级测试，不能只根据总体功能介绍做判断。

如果把这几条路线放在一起比较，可以这样总结：

Lupine 作为主要概念验证路线；

Juice 用于跨平台和产品化部署对照；

Cricket 用于传统远程过程调用和受控应用对照；

SCUDA 用于代码生成和接口定制参考；

mrCUDA 用于运行中迁移研究；

TensorFusion 用于统一平台设计参考。

也就是说，Lupine、Juice 和 Cricket 是当前可以进行应用兼容性验证的远端调用候选；SCUDA、mrCUDA 和 TensorFusion 分别提供代码生成、状态迁移和平台架构三个不同方向的参考。

---

### 4. 启动前选择本地或远端

本地和远端两条数据路径准备好以后，还需要平台控制层完成选择、预留和容器配置。

控制层收到逻辑 GPU 请求后，先过滤不满足硬件、版本和权限要求的候选，再按照本地优先、排队时间、网络延迟、数据位置或成本进行评分。

选中本地时，最终工作负载携带 NVIDIA 设备插件或 HAMi 的资源请求。

选中远端时，最终工作负载携带客户端接口适配库、远端 GPU 资源端点、运行会话和访问凭据。

每次运行只生成其中一种配置。

控制层有三种实现方式。

#### 4.1 路线一：Kubernetes 准入改写机制

原文中的 Admission Webhook，可以讲成“Kubernetes 准入改写机制”。

它在工作负载创建之前检查并修改配置。选中本地时，它写入 GPU 资源请求；选中远端时，它加入客户端适配库、环境变量、挂载目录或初始化容器。

这条路线实现较短，适合概念验证。

准入请求需要同步返回，适合读取已经准备好的资源摘要。复杂排队、多轮重试和长时间远端预留，会增加工作负载创建延迟。

#### 4.2 路线二：自定义工作负载和控制器

第二种方式是定义一个“加速器工作负载”对象，代码中的资源名称可以叫 `AcceleratorWorkload`。

它通过 Kubernetes 自定义资源定义，也就是 CRD，实现一套新的资源接口。用户提交加速器工作负载，控制器完成资源选择和预留，然后再创建真正运行的容器工作负载。

控制器可以记录以下状态：

- `Pending`，等待处理；
- `Selecting`，正在选择资源；
- `Reserved`，已经完成预留；
- `Running`，任务正在运行；
- `Releasing`，正在释放资源；
- `Succeeded` 或 `Failed`，任务成功或失败。

远端 GPU 主机上还可以运行一个“远端节点代理”。它负责上报 GPU 状态、建立运行会话、刷新租约和清理任务进程。

这条路线允许异步等待和重试，也能完整记录选择理由、设备身份、运行组件版本和释放结果，适合多个远端 GPU 主机和生产环境。

#### 4.3 路线三：Kubernetes 动态资源分配

第三种方式是使用 Kubernetes 动态资源分配，英文简称 DRA。

DRA 中的 `ResourceClaim` 可以讲成“资源申请对象”，`DeviceClass` 可以讲成“设备类型对象”。它们用于描述工作负载需要什么设备，以及最终绑定到哪一个设备。

本地整卡、MIG 实例、HAMi 软件份额和远端 GPU 资源端点，都可以逐步纳入统一的资源属性。

资源绑定完成后，平台仍要根据结果装入本地驱动环境或者远端客户端适配库。

DRA 更适合远端资源目录、运行会话和配额模型成熟后的长期演进。当前阶段先把远端调用和资源预留跑通，实施风险更容易控制。

三种方式可以简单概括：

准入改写机制适合快速验证；

自定义工作负载和控制器适合生产落地；

动态资源分配适合长期统一资源模型。

---

### 5. 推荐的完整方案

结合前面的分析，我建议分三个阶段建设。

#### 第一阶段：验证真实业务能否远端运行

本地采用 NVIDIA GPU 运维控制器和 NVIDIA 设备插件，先支持整卡。

远端以 Lupine 为主进行概念验证。

控制层可以先采用轻量准入改写机制，或者功能收敛的自定义控制器，只支持本地和远端二选一。

测试直接使用真实业务镜像，至少覆盖：

- PyTorch 基础张量计算；
- 模型加载和一次完整推理；
- 显存分配、释放和显存不足；
- CUDA 执行流和异步复制；
- NVML 查询；
- 自定义 CUDA 算子；
- 业务需要时再测试多 GPU 和 NCCL。

NCCL 是 NVIDIA 多 GPU 集合通信库，主要用于多张 GPU 之间的数据同步。

第一阶段要形成一份兼容矩阵，记录应用镜像、框架版本、CUDA 版本、客户端适配库版本、服务端版本和 NVIDIA 驱动版本。

同时要测量本地与远端的吞吐、平均延迟、P95/P99 尾延迟、GPU 利用率、网络流量和客户端 CPU 开销。

这一阶段最终回答三个问题：真实业务能否运行，性能损耗是多少，当前兼容边界在哪里。

#### 第二阶段：建立可管理的远端 GPU 资源池

引入加速器工作负载、平台控制器和远端节点代理。

建立远端 GPU 资源目录，加入资源预留、运行会话、租约、心跳检测和幂等回收。

控制器先绑定资源，再创建实际工作负载。任务结束后，正常退出、异常退出和租约过期都能触发清理。

安全侧加入 TLS 或双向 TLS、短期凭据、租户授权、网络隔离和审计日志。双向 TLS 表示客户端和服务端互相验证证书。

这一阶段把“能够远端调用”升级为“多个任务能够可靠、安全地使用一个远端 GPU 资源池”。

#### 第三阶段：提高利用率并统一调度

本地侧按需求加入 HAMi、Volcano 或 KAI，处理 GPU 切分、队列、公平性和拓扑。

资源模型稳定后，再评估 Kubernetes 动态资源分配，把本地整卡、MIG、软件份额和远端 GPU 端点纳入统一申请方式。

整个实施顺序是：先验证调用链，再完善资源控制，最后统一调度模型。

---

### 6. 落地时需要重点验证的风险

第一是兼容性。

远端运行组件要覆盖业务真正使用的 CUDA、NVML、cuBLAS、cuDNN 和自定义算子。经过验证的版本组合可以固化成“运行环境兼容配置”，调度时只选择匹配的远端端点。

第二是性能。

远端调用把原来的本机调用变成网络往返。GPU 计算核函数运行时间较长、数据能够批量传输的任务通常更合适；大量小计算核函数、频繁同步和强多卡通信的任务对网络延迟更敏感。

第三是多 GPU。

一个客户端能够看到多台服务端上的 GPU，只代表设备可以被枚举。跨服务端的显存复制、多 GPU 对等访问、设备拓扑和 NCCL 通信仍要分别测试。

第四是资源一致性。

远端 GPU 端点要有唯一身份和明确容量。平台通过原子预留、运行会话和租约，保证一项独占资源只分配给一个任务。

第五是故障处理。

GPU 服务端宕机或网络长时间中断时，当前运行会话通常会失败。第一版可以依靠上层任务重新执行，或者从业务检查点恢复。

网络请求重试也要区分接口类型。只读查询可以直接重试；显存分配、释放和计算启动等操作要通过请求编号、顺序号和会话状态去重，避免一次操作被执行两遍。

第六是安全和多租户。

远端 GPU 服务端能够分配显存、执行计算和读取设备信息，需要加密传输、身份认证、会话级授权和审计。NVML 返回的进程、设备序列号和利用率信息也要按租户权限过滤。

第七是可观察性。

平台选择记录、客户端日志、网络指标、远端运行会话和 GPU 指标，应当使用同一个工作负载编号关联。排障时才能判断问题发生在平台控制器、客户端、网络、GPU 服务端还是 NVIDIA 驱动。

第八是开源合规和维护状态。

需要检查仓库许可证、附加条款、第三方依赖、最近维护情况和发布镜像。实际采用时要固定项目版本和镜像摘要，避免上游变化导致环境漂移。

---

### 7. 总结

最后总结一下。

整套方案可以看成三层。

底层是本地 GPU 能力，由 NVIDIA GPU 运维控制器、NVIDIA 设备插件、HAMi 和调度器组成。

另一条数据路径是远端 GPU 调用，由客户端接口适配库、网络协议和远端 GPU 服务端组成。

中间的平台控制层负责读取逻辑请求、比较候选、预留资源，并生成本地或远端运行环境。

近期目标是实现启动前透明选择：业务不填写 GPU 地址，继续使用原有 CUDA 接口，一次运行固定在已经选定的路径上。

推荐的中期组合是：

本地以 NVIDIA GPU 运维控制器和设备插件为基础，按需加入 HAMi；

远端优先验证 Lupine；

控制层采用加速器工作负载、平台控制器和远端节点代理。

实施上先验证真实业务，再建立资源预留和会话管理，最后扩展本地共享与统一调度。

## 二、可能被问到的问题与建议回答

### 1. 为什么远端 GPU 不能直接交给 NVIDIA 设备插件管理？

答：

NVIDIA 设备插件管理的是工作负载所在节点能够直接访问的本地设备。远端 GPU 没有出现在该节点的 Linux 设备文件中，还需要客户端适配库把 CUDA 调用转发到远端服务端。

设备插件可以表达本地资源，远端路径还要增加网络调用和会话管理。

### 2. 方案中的“透明”具体做到什么程度？

答：

业务只提交逻辑 GPU 请求，不填写远端地址，原有 CUDA/NVML 调用方式保持不变。平台负责选择资源和装入运行环境。

当前透明范围是启动前选择和运行期间固定绑定。目标应用的兼容程度由测试矩阵给出。

### 3. 为什么任务运行后不自动从远端切回本地？

答：

运行中的任务已经产生 CUDA 上下文、显存数据、执行流、同步事件和库句柄。切回本地需要迁移或重建这些状态。

当前方案让任务保持原绑定。运行中迁移可以作为后续独立研究课题。

### 4. 普通 CPU 节点能使用远端 GPU 吗？

答：

可以。节点需要满足客户端适配库、动态链接库、网络和证书要求。远端模式不申请本地 `nvidia.com/gpu` 资源，因此可以运行在普通 CPU 节点。

### 5. `libcuda.so.1` 到底是什么？

答：

它是 Linux 中提供 CUDA 驱动接口的动态库文件。应用进行设备初始化、显存分配和启动 GPU 计算时，会调用这个库中的函数。

远端方案提供一个同名替代库，把原本发往本地驱动的调用转发到远端 GPU 服务端。

### 6. `libnvidia-ml.so.1` 是什么？

答：

它是 Linux 中提供 NVML 管理接口的动态库文件。`nvidia-smi` 会通过它查询 GPU 型号、显存、利用率和进程信息。

远端替代库可以把这些查询转发到远端服务端。

### 7. 为什么第一阶段优先验证 Lupine？

答：

Lupine 公开了客户端、服务端、代码生成工具、容器构建文件、测试和版本化镜像，比较容易搭建一套可重复的验证环境。

它是概念验证主线。是否进入生产基线，还要看真实业务兼容性、性能、安全和维护情况。

### 8. Juice 和 Cricket 的价值在哪里？

答：

Juice 适合评估 Linux、Windows、虚拟机和容器混合环境。Cricket 适合应用构建方式固定、CUDA 接口范围可控的远程调用场景。

第一阶段可以做针对性对照，避免同时维护多套相似环境。

### 9. 为什么不直接采用 TensorFusion 这类一体化平台？

答：

一体化平台值得验证。评估时要逐项确认公开版本中已经实现的模块、成熟度、许可证和企业功能边界。

如果实测能够满足需求，可以调整组合方式。当前拆分路线便于逐层验证和替换组件。

### 10. `nvidia-smi` 能运行，是否表示远端方案已经可用？

答：

它主要验证 NVML 查询。真实业务还会使用 CUDA 驱动接口、运行时接口、显存、GPU 计算核函数、执行流、cuBLAS、cuDNN 和自定义算子。

最终验收要运行完整业务。

### 11. PyTorch、vLLM 和自定义 CUDA 算子能否直接运行？

答：

结果取决于框架版本、动态链接方式、依赖库和远端运行组件的接口覆盖。每个目标镜像都要执行兼容测试。

平台只把已经验证的版本组合列入支持范围。

### 12. 客户端和服务端的 CUDA 版本怎样匹配？

答：

兼容配置中要记录应用 CUDA 版本、客户端适配库版本、代码生成所依据的 CUDA 头文件版本、服务端版本和 NVIDIA 驱动版本。

平台在选择远端端点时先完成版本过滤，避免任务启动后才发现接口缺失。

### 13. 远端 GPU 的性能会下降多少？

答：

性能取决于网络往返延迟、带宽、GPU 计算粒度、显存复制量和同步频率，没有统一比例。

要在同一业务上对比本地与远端吞吐、尾延迟、GPU 利用率、网络流量和客户端 CPU 开销。

### 14. 哪类任务更适合远端 GPU？

答：

计算密集、GPU 计算时间较长、数据可以批量传输的任务通常更合适。

大量小计算、频繁同步、严格低延迟和强多卡通信的任务，需要更谨慎的性能评估。

### 15. 多 GPU 和 NCCL 怎样处理？

答：

需要分别测试同一服务端多卡、跨服务端多卡、设备间显存复制、多 GPU 对等访问、设备拓扑和 NCCL。

设备能够显示出来，只代表枚举成功；通信语义和性能需要独立验证。

### 16. 能否使用 RDMA 提升性能？

答：

RDMA 的中文是远程直接内存访问。它能否发挥作用，取决于远端运行组件是否实现了对应传输路径。

网卡支持 RDMA，并不会自动改变基于 TCP 或 HTTP/2 的调用方式。

### 17. 怎样比较一张本地 GPU 和一个远端 GPU 端点？

答：

先比较硬条件，包括型号、显存、切分类型、隔离等级、版本兼容性和权限。

通过硬条件后，再比较排队时间、网络延迟、数据位置和使用成本。第一版建议采用清晰、可解释的规则。

### 18. 本地 HAMi 份额和远端整卡怎样选择？

答：

由任务的显存、算力和隔离要求决定。允许共享并且本地份额满足要求时，可以优先本地；要求独占或稳定性能时，可以选择远端整卡。

资源模型要明确记录整卡、MIG 和软件份额，不能都简化成“一张 GPU”。

### 19. 怎样防止远端 GPU 被重复分配？

答：

平台控制器通过原子预留建立运行会话和租约，预留成功后才创建业务容器。远端节点代理只接受持有有效会话凭据的任务。

任务结束或租约过期后，平台执行幂等回收。

### 20. 远端 GPU 资源端点需要保存哪些信息？

答：

至少包括 GPU 主机、具体设备或设备组、型号、显存、运行组件版本、容量、健康状态、租户、运行会话、租约和访问策略。

IP 地址和端口只是其中的连接信息。

### 21. 为什么生产环境更适合自定义控制器？

答：

控制器支持异步等待、状态记录、重试、取消和幂等回收。Kubernetes 准入改写机制需要同步返回，更适合快速、确定的配置修改。

远端主机数量增加后，控制器更容易管理资源预留和异常状态。

### 22. Kubernetes 动态资源分配能否取代控制器和远端运行组件？

答：

动态资源分配提供设备申请与绑定框架。远端 GPU 资源目录、运行会话、租约、节点代理和客户端适配库仍然需要实现。

未来可以把部分控制能力封装成动态资源分配驱动。

### 23. 远端 GPU 服务端运行中宕机怎么办？

答：

当前运行会话标记失败，平台回收租约，再按照任务策略重新创建。业务有检查点时，可以从检查点恢复。

第一版不承诺 CUDA 上下文在不同服务端之间无损续跑。

### 24. 网络抖动时可以直接重试 CUDA 调用吗？

答：

需要根据接口语义处理。只读查询或者明确可重复执行的请求可以重试。

显存分配、释放和计算启动等操作，需要利用请求编号、顺序号和会话状态去重。语义不明确时，由整个任务重新执行更安全。

### 25. 怎样保证远端 GPU 访问安全？

答：

使用 TLS 或双向 TLS、短生命周期凭据、租户授权、网络策略和审计日志。凭据要和工作负载、运行会话、远端端点及过期时间绑定。

NVML 信息按权限过滤，减少跨租户暴露设备和进程细节。

### 26. 任务异常退出后怎样释放 GPU？

答：

正常退出由平台主动关闭运行会话；异常退出通过工作负载终止事件、租约超时和远端节点代理心跳触发回收。

服务端清理关联进程和 CUDA 上下文，清理操作可以安全地重复执行。

### 27. 第一版最小可行产品包含哪些能力？

答：

建议只支持 Linux 容器、一个目标 CUDA/PyTorch 组合、单 GPU 整卡和一种远端运行组件。

功能包括逻辑请求、本地或远端选择、远端资源预留、客户端适配库注入、资源释放、基础认证和监控。

### 28. 概念验证怎样验收？

答：

同一业务镜像能够在本地和远端完成任务；目标框架与关键接口测试通过；并发任务不会重复分配同一资源；正常和异常结束都能回收 GPU；性能数据处于预设范围。

验收报告还要明确当前未支持的接口、框架版本和工作负载类型。

### 29. 这项建设的收益怎样衡量？

答：

观察 GPU 利用率、任务排队时间、任务成功率、单位任务成本和业务接入成本。

最终使用范围由资源收益、远端性能损耗、网络成本和平台维护成本共同决定。
