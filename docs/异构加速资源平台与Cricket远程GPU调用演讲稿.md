## 开场

各位好，今天我汇报的内容包括两个部分。

第一部分，是 Cricket 独立远程 GPU 调用；第二部分，是异构加速资源平台适配层。

Cricket 已经完成真实的远端 GPU 调用实验，证明调用端程序可以通过网络使用另一台机器上的 GPU。平台适配层已经完成资源建模、资源选择、资源租约、运行计划和控制器恢复等控制逻辑，并通过模拟实验进行了验证。

# 第一部分：Cricket 独立远程 GPU 调用

## Cricket 的基本原理

首先是Cricket

CUDA 程序和 CPU 业务逻辑仍然运行在调用端。程序启动时，通过 Linux 的动态库预加载机制，优先加载 Cricket 提供的客户端动态库。

这个客户端动态库提供了 CUDA 接口的包装函数。因此，程序调用显存申请、数据复制、启动计算核心或者释放显存时，调用会先进入 Cricket 客户端，而不是直接访问本机 GPU。

客户端把接口参数和需要传输的数据整理成远程请求，通过网络发送给 GPU 端。GPU 端运行 Cricket 服务端。服务端收到请求以后，再调用真实的 CUDA 和 GPU，最后把返回值或者计算结果送回调用端。


## 两端环境和职责


调用端负责运行程序的 CPU 部分、准备输入数据、加载 Cricket 客户端、发起远程请求，并在结果返回后完成校验。调用端可以没有本地 NVIDIA GPU，但需要具备运行程序所需的 Linux 环境、动态库和网络连接。

GPU 端负责运行 Cricket 服务端，并提供真实的 CUDA、驱动和 NVIDIA GPU。当前实验中的 GPU 端是 Windows 加 WSL 环境，外部通过固定的 Windows 网络入口访问，内部再转发到 WSL 中的 Cricket 服务。


## Cricket 的构建和启动

> 对应第 3 章“第一次构建 Cricket”

第三章记录了 Cricket 的源码版本、依赖库、CUDA 环境和构建步骤。现场不需要逐条讲安装命令，只需要关注最后生成的两个主要程序：一个是 GPU 端运行的 Cricket 服务端，另一个是调用端加载的 Cricket 客户端动态库。

服务端启动以后等待远程请求；调用端启动 CUDA 程序时，设置远端地址、远程调用版本和客户端动态库路径。两端版本和参数一致以后，CUDA 调用才会进入远端链路。

## 实验一：基础接口测试


第一个实验是最小的基础接口测试。

程序先查询设备数量，然后申请一块显存，写入固定内容，最后释放显存。实验结果中，设备查询、显存申请、显存写入和显存释放全部返回成功，并且调用端发现了一个远端 GPU。

这个实验主要确认三件事：调用端能够连接到服务端，服务端能够访问真实 GPU，基础的显存管理接口可以通过远程调用完成。

不过，这个阶段还没有执行自定义计算核心，也没有验证计算结果，所以它只是整条链路的基础检查。

## 实验二：计算核心与逐元素校验


第二个实验加入了完整的计算过程。

调用端先生成从 0 到 255 的一组数据，然后把数据传到远端显存。远端 GPU 对每个元素加一，等待计算完成后，再把结果传回调用端。最后，调用端使用 CPU 对全部结果逐个检查。

实验输出的样例是 1、2 和 256，全部 256 个元素都没有错误。

这说明输入数据上传、远端计算、计算同步、结果返回和本地校验已经形成完整闭环。和第一个实验相比，这一步不只是证明接口能调用，而是证明远端 GPU 确实完成了计算，并且返回了正确结果。

## 实验三：矩阵全连接层


第三个实验使用一个更完整的矩阵任务。

输入是两个 512 乘 512 的矩阵，计算过程包括矩阵乘法、加偏置和激活运算，一共包含一亿多次乘加。输入数据由调用端生成，通过 Cricket 传到远端，远端 GPU 连续完成两个计算阶段，结果再返回调用端。

调用端没有只检查几个样例，而是使用 CPU 对二十六万多个输出进行完整复算和逐项比较。最终 GPU 结果和 CPU 结果一致，没有发现不匹配。

这个实验说明，Cricket 不只能够完成最小接口和简单计算，也能够承载数据量更大、计算阶段更多的任务。

这里的结论仍然是远程执行和结果正确

# 第二部分：异构加速资源平台适配层


## 平台要解决的问题


如果没有统一平台，本地 GPU 和远端 GPU 会形成两套不同的使用流程。

本地任务需要查询节点、设备插件资源和容器资源申请；远端任务需要查询服务器地址、设备状态和连接参数。业务如果直接处理这些内容，就会和具体节点、资源名称以及远端技术绑定。

因此，平台让用户只提交一份统一的资源需求，例如需要一个 NVIDIA GPU，允许自动选择，并且本地优先。本地和远端的具体差异由平台负责处理。


## 平台总体架构

总体架构是这样的：

用户提交的统一任务。任务进入控制器以后，平台一边进行资源盘点，一边根据用户设置执行选择策略。

资源盘点会把本地节点和远端入口整理成统一的候选资源。选择策略只面对这些候选资源，不需要直接理解每一种底层技术。

选择完成以后，平台保存选择结果，再创建资源租约，最后由适配器生成运行计划。

运行计划以前属于控制面，负责选择、记录和准备；真正启动程序、传输数据和执行 GPU 计算属于后续执行层。

平台决定使用哪一类加速资源和哪个目标；如果选择本地资源，真实容器最终仍要经过调度器和节点运行。

## 本地和远端的选择


平台先把不同来源的资源整理成统一候选，然后根据任务要求进行过滤。

当前定义了三种模式：仅本地、仅远端和自动选择。自动模式默认本地优先，本地不能完整满足时再检查远端。

如果用户指定仅本地，本地不足时不能擅自改用远端；如果用户指定仅远端，即使存在合适的本地资源，也不能改变用户选择；如果两边容量都不够，平台返回当前不可调度。


## 一次任务的控制过程

一次任务进入平台以后，首先进行输入校验，然后读取当前资源，生成候选，按照模式和策略作出选择。

选择结果会被写入任务状态，记录选中了本地还是远端、哪个资源池和哪个目标。之后平台创建资源租约，用来记录这份容量属于哪个任务。

选择结果和资源租约承担不同职责：选择结果说明平台选了什么以及选择原因，资源租约说明这份资源当前归谁使用。

资源确定以后，适配器根据租约生成运行计划。本地计划可以包含资源申请和节点约束；未来的远端计划可以包含连接地址、动态库和运行参数。

任务结束、删除或者启动前失败时，平台进入释放流程。资源清理完成后，租约进入已释放状态，容量重新参与下一次选择。

## 平台中的核心对象

> 对应第 6 章“五类核心对象”

文档接下来介绍了五类核心对象，这里简单对应一下。

资源提供者描述一种后端具备什么能力；资源池把同一类资源组织在一起；远端入口描述一个远端运行位置；用户任务保存资源需求和平台选择；资源租约保存一次已经确定的资源所有权。

这些对象把配置、任务意图、选择结果和资源所有权分开，使控制器重启或者配置变化以后，已有分配仍然可以恢复和清理。

## 控制面正确性设计

> 对应第 7 章“正确性设计”

这一章主要解决并发和重复执行问题。

资源租约从创建时就要参与容量计算，否则两个任务可能在租约状态还没来得及更新时重复选择同一份资源。

对于排他的远端入口，仅靠资源盘点快照也不够。两个任务可能同时看到入口空闲，所以最终预留还需要一个原子占用记录，保证只有一个任务成功。

另外，Kubernetes 控制器会重复执行。相同任务的预留、绑定和释放必须可以安全重试，不能因为控制器重启或者网络抖动就创建第二个任务、第二份租约或者第二次容量扣减。

## 模拟实验设计


完成控制面设计以后，文档使用五类模拟实验进行验证。

模拟实验不依赖现场是否有 GPU，可以稳定覆盖资源选择、容量计算、并发占用和控制器恢复。这些实验验证的是平台控制逻辑，不代替真实容器和真实 GPU 验收。

## 模拟实验一：选择策略

> 对应第 10 章

第一个实验验证仅本地、仅远端和自动选择。

它检查本地和远端都可用时自动模式是否选择本地，本地不足时是否检查远端，固定模式是否严格遵守用户意图，以及容量或资源形态不匹配时是否返回不可调度。

这个实验说明平台能够正确进行资源选择，但不说明选中的远端资源可以真实执行计算。

## 模拟实验二：资源盘点和容量

> 对应第 11 章

第二个实验验证整卡、切分资源和共享资源能否被正确区分，也检查已经运行的任务和已经创建的租约怎样扣减容量，以及同一份占用会不会被重复计算。

这个实验说明平台能够把资源账目算清楚，但不代表真实设备插件和硬件隔离已经完成验收。

## 模拟实验三：本地任务控制闭环

> 对应第 12 章

第三个实验模拟任务从提交、选择、创建租约、生成运行计划和创建容器任务对象，到模拟运行成功并释放租约的完整过程。

这个实验说明控制面状态能够形成闭环。不过这里的容器只是模拟对象，没有真正经过调度器、节点和 GPU。


## 模拟实验五：控制器恢复

> 对应第 14 章

第四个实验验证控制器重复执行和重启恢复。

实验预先创建已有租约或者任务对象，再多次执行控制器，检查它是否继续使用原来的选择、重新关联已有对象，并避免创建第二个任务。

这个实验说明控制器能够恢复管理状态，但不代表应用进程、GPU 显存和正在执行的计算可以恢复。

## 后续计划与结论

> 对应第 16～17 章

第二份文档最终形成的控制链是：统一任务意图，经过资源盘点和本地、远端选择，生成可以解释的选择结果，创建可以恢复的资源租约，再形成运行计划。

模拟实验分别验证了选择、容量、生命周期、并发占用和控制器恢复。它们足以说明平台适配层具备一致性和扩展基础，但不能把模拟结果写成真实容器或者真实远端 GPU 已经通过平台运行。

后续接入时，平台需要把 Cricket 服务端登记成一个真实远端入口。平台选中它以后创建资源租约，由 Cricket 适配器根据租约生成远端地址、客户端动态库和连接参数，再由执行器创建真实任务。

任务启动后，CUDA 调用通过 Cricket 转发到远端 GPU；任务完成以后，平台记录结果并释放租约。最终需要形成的链路是：

```text
统一提交
  → 平台选择远端资源
  → 创建资源租约
  → 生成 Cricket 运行计划
  → 启动真实任务
  → 远端 GPU 完成计算
  → 返回并校验结果
  → 释放资源
```

因此，目前可以确认的是：Cricket 已经独立证明远端 GPU 调用可行，平台适配层已经独立证明资源管理控制链成立。下一阶段的工作，是按照第二份文档中的运行计划和执行器边界，把两部分正式接入并完成组合验收。

# 备用问答

> 以下内容不属于演讲正文，只在交流环节使用。

## 1. 平台和 Kubernetes 调度器是什么关系？

平台负责选择使用哪一类加速资源以及哪个目标。如果选择本地资源，容器仍然需要经过 Kubernetes 调度器完成节点调度。平台补充加速资源选择，不替代通用调度器。

## 2. Cricket 是不是把远端 GPU 直接挂载到了调用端？

不是。Cricket 接管 CUDA 接口调用，通过网络让远端服务端调用真实 GPU。调用端没有直接获得远端物理设备。

## 3. Cricket 是不是只安装客户端动态库就可以使用？

还需要应用动态链接 CUDA、远端服务已经启动、网络可达、依赖库完整，并且客户端、服务端和 CUDA 环境相互兼容。

## 4. 程序在 GPU 端编译，是不是也在 GPU 端运行？

不是。当前实验在 GPU 端编译是为了使用目标 CUDA 环境，编译完成后把程序复制回调用端。业务进程在调用端运行，GPU 计算发生在远端。

## 5. 矩阵实验能否证明远端 GPU 性能更高？

不能。它主要证明较复杂任务能够远程执行并返回正确结果。性能还需要单独比较计算量、传输量、网络延迟和调用次数。

## 6. 自动选择是不是运行中的无缝迁移？

不是。当前指任务启动前的资源选择。运行中的任务迁移还需要恢复进程、内存、GPU 显存和计算状态。

## 7. 控制器恢复和应用恢复有什么区别？

控制器恢复是重新读取选择结果、租约和任务对象；应用恢复还需要恢复程序和 GPU 计算状态。当前模拟实验验证的是控制器恢复。

## 8. 当前是否支持多个任务共享同一张远端 GPU？

当前不声明这种能力。现阶段使用排他远端入口。多任务共享还需要显存、算力、会话和故障隔离机制。

## 9. 五个模拟实验与 Cricket 实验有什么区别？

五个模拟实验验证平台会不会正确选择、记账、占用、恢复和释放资源；Cricket 实验验证远端 GPU 能不能真实执行计算。两类实验不能互相替代。

## 10. 怎样判断两部分已经真正接通？

需要在同一次任务中看到平台选择远端、租约创建、Cricket 配置自动生成、真实任务启动、远端计算结果校验通过，以及租约最终释放。

## 11. 一个新的后端怎样接入平台？

接入一个后端，不是把它的调用代码直接写进主控制器，而是按照平台已经划分好的边界补齐几部分能力。

首先，要说明这种后端支持什么设备、支持本地还是远端、使用整卡还是共享资源。其次，要让资源盘点模块能够把它的资源整理成平台统一的候选资源。然后，实现这个后端的适配器：资源提供部分负责校验配置并生成运行计划，资源分配部分负责预留、绑定和释放容量。最后，还要由执行器根据运行计划启动真实任务、观察结果并完成清理。

如果接入的是远端后端，还需要定义远端入口怎样登记、怎样探测健康状态、怎样保存地址和版本、多个任务怎样避免重复占用，以及远端失败怎样转换成平台可以理解的任务状态。

因此，一种后端完成接入，至少要走通下面这条链路：

```text
声明后端能力
  → 资源进入统一盘点
  → 平台能够选择
  → 创建资源租约
  → 生成后端运行计划
  → 执行器启动真实任务
  → 返回状态和结果
  → 释放资源
```

## 12. 后端接入最难的地方是什么？

难点通常不在于增加一个接口名称，而在于把控制面的抽象和真实运行环境对应起来。

第一个难点是运行环境。客户端和服务端可能要求特定的操作系统、驱动、工具包、动态库和版本组合。以 Cricket 为例，还要处理动态 CUDA 运行库、客户端动态库、远端服务版本和 GPU 架构兼容问题。

第二个难点是运行环境怎样交付给任务。可以把客户端和依赖制作成独立运行时镜像，再由启动前的准备容器复制到共享目录；也可以制作包含客户端的业务基础镜像；在受控环境中还可以使用节点预装和目录挂载。不同方案在镜像维护、可移植性、权限和安全性方面各有取舍，需要根据部署环境确定。

第三个难点是网络和安全。远端地址怎样发现，网络是否可达，是否需要认证、加密、防火墙和访问控制，都不能只依赖应用自己处理。如果后端本身没有认证和加密能力，就需要通过可信网络、网关或者额外代理进行保护。

第四个难点是资源隔离和容量核算。平台必须知道一个远端入口代表一张卡、多张卡还是一个共享会话，也要知道它能否被多个任务同时使用。如果数据面不能提供可靠隔离，控制面就只能采用排他分配，不能仅通过修改一个数量字段就宣称支持共享。

第五个难点是状态和故障映射。连接失败、运行库不兼容、镜像启动失败、远端设备故障和应用自身报错，处理方式并不相同。接入时需要明确哪些错误可以重试、哪些可以重新选择资源、哪些应该直接返回给用户。

因此，后端接入通常需要同时给出运行环境方案、网络方案、资源隔离方案、版本兼容方案和故障处理方案，而不只是实现几个代码接口。

## 13. 本地 GPU 使用 HAMi，平台是否支持？

从平台控制面的设计看，可以接入 HAMi 提供的 Kubernetes 扩展资源。平台的本地资源模型能够描述整卡、切分资源、软件共享和自定义资源名称，也能够把配置好的扩展资源写入容器的申请量和限制量。

如果 HAMi 已经在目标集群中安装，并通过设备插件向 Kubernetes 节点发布对应的扩展资源，平台可以把这个资源名称配置到本地资源池中，再按照普通本地候选进行盘点、选择和注入。

但这里需要区分“平台能够使用 HAMi 发布的资源”和“平台自己实现 HAMi 虚拟化”。平台不会创建 HAMi 设备、控制显存或算力比例，也不负责执行底层隔离；这些仍然由 HAMi、设备插件、节点组件和实际 GPU 环境负责。

所以准确的回答是：

> 平台在资源接口和控制流程上可以适配 HAMi，但真实可用性取决于目标集群中的 HAMi 部署、资源名称、设备上报、调度规则和隔离能力，仍然需要在真实 GPU 集群中进行验收。

验收时至少要检查：平台能发现 HAMi 资源，任务能被选择到正确节点，容器申请值与限制值正确，容器能看到预期设备，显存和算力限制实际生效，并且任务结束后容量能够重新使用。

## 14. 平台是否可以支持不同的远端调用技术？

平台层的设计是可扩展的，因为主控制器不直接依赖 Cricket，也不直接调用某一种远端接口。资源盘点、选择策略、资源租约和运行计划使用的是统一合同，具体后端差异由适配器和执行器处理。

因此，未来可以接入其他远端 GPU 服务、远端 NPU、外部作业系统或者由代理程序管理的加速资源。不同后端可以使用不同的连接方式，例如动态库转发、命令行客户端、网络服务接口、远端代理或者外部作业提交接口。

不过，“架构上允许接入”不等于“无需开发就自动支持”。每增加一种后端，仍然需要实现并验证：

- 它的资源怎样被发现和描述；
- 它支持哪些设备和分配粒度；
- 怎样预留和释放资源；
- 怎样生成运行计划；
- 客户端环境怎样交付；
- 怎样启动、观察和停止任务；
- 错误怎样转换成平台状态；
- 安全、版本和隔离怎样保证。

因此可以把平台的灵活性理解为：

> 平台已经把通用控制流程和具体远端技术分开，新后端可以沿着统一边界接入；但每一种远端数据面都需要自己的适配实现、环境方案和真实验收。

# 补充参考资料：Kubernetes、HAMi 与平台的关系

> 本节不属于演讲正文，不需要主动讲解。用于回答 Kubernetes、容器、HAMi、本地 GPU 和平台分层方面的追问。

## 1. Kubernetes 是什么？

Kubernetes，通常简称 K8s，是一个容器编排和集群管理系统。它管理多台机器以及运行在这些机器上的容器任务。

容器主要解决“程序带着什么环境运行”，其中可以包含业务程序、依赖库、文件和启动命令。Kubernetes 在这个基础上继续处理：

- 容器任务放到哪台机器；
- CPU、内存和扩展资源是否足够；
- 任务怎样启动、停止和重新创建；
- 多个任务怎样使用网络和存储；
- 用户声明的期望状态怎样持续保持。

Kubernetes 实际调度的基本单位叫 Pod。一个 Pod 可以包含一个或多个容器，这些容器位于同一节点，并共享部分网络和存储环境。

可以简单区分为：

```text
Docker、containerd 等容器运行时
  → 在一台机器上真正创建和运行容器

Kubernetes
  → 在多台机器之间安排和持续管理容器任务
```

## 2. 普通 Kubernetes 怎样使用 GPU？

Kubernetes 本身不会直接识别和分配物理 GPU，需要依靠驱动、容器 GPU 运行环境和设备插件。

```text
物理 GPU
  → NVIDIA 驱动
  → 容器 GPU 运行环境
  → Kubernetes 设备插件
  → 向节点上报 GPU 扩展资源
  → Kubernetes 调度 GPU Pod
```

设备插件向 Kubernetes 上报类似 `nvidia.com/gpu` 的扩展资源。Pod 申请这类资源后，Kubernetes 把它调度到有足够容量的节点，设备插件再完成实际设备分配。

我们的平台不直接操作物理 GPU，也不替代设备插件。平台负责盘点、选择、租约和运行计划；设备插件负责把实际设备交给容器。

## 3. HAMi 是什么？

HAMi 是建立在 Kubernetes 体系中的异构加速器管理和虚拟化中间件。它不是 Kubernetes 的替代品，而是补充 Kubernetes 对 GPU、NPU 等加速器的设备感知调度、共享、切分和隔离能力。

HAMi 通常包含设备插件、调度扩展、Pod 修改组件、设备相关的容器内虚拟化组件，以及监控组件。不同设备的具体能力取决于厂商、型号、驱动和对应后端。

普通整卡分配通常是：

```text
一个任务申请一张 GPU
  → 整张 GPU 分配给这个任务
```

HAMi 希望进一步支持：

```text
一张物理 GPU
  → 任务 A 使用一部分资源
  → 任务 B 使用一部分资源
  → 任务 C 使用一部分资源
```

HAMi 负责具体设备选择，以及在设备后端支持的情况下实施显存或算力限制。软件共享和 MIG 硬件切分不是同一种方式，实际隔离能力需要在目标硬件上验证。

官方资料：[HAMi 项目](https://github.com/Project-HAMi/HAMi)、[HAMi 架构说明](https://project-hami.io/docs/core-concepts/hami-architecture)。

## 4. Kubernetes、HAMi 与我们的平台怎样分工？

三者可以放在下面这张图中理解：

```text
                    我们的平台
        统一任务、资源盘点、选择、租约、运行计划
                         │
             ┌───────────┴───────────┐
             │                       │
          选择本地                选择远端
             │                       │
             ▼                       ▼
        Kubernetes                远端适配器
             │                       │
       HAMi / 设备插件            Cricket 等后端
             │                       │
          本地 GPU                 远端 GPU
```

我们的平台负责：

- 用户需要什么加速资源；
- 允许使用本地还是远端；
- 选择哪个资源池和目标；
- 创建资源租约；
- 保存选择结果；
- 生成运行计划；
- 任务结束后释放平台资源。

Kubernetes 负责：

- 创建和管理真实 Pod；
- 在集群节点之间调度 Pod；
- 管理容器生命周期；
- 管理通用网络、存储和期望状态。

HAMi 在选择本地共享加速资源时负责：

- 上报和管理加速设备；
- 进行设备感知调度；
- 选择具体设备；
- 分配共享份额；
- 在设备后端支持时实施显存或算力限制。

Cricket 在选择远端 GPU 时负责：

- 接管 CUDA 调用；
- 通过网络转发请求和数据；
- 让远端服务端调用真实 GPU；
- 把计算结果返回调用端。

## 5. 平台是否支持 HAMi？

从控制面模型看，平台可以使用 HAMi 向 Kubernetes 发布的扩展资源。平台已经能够表达整卡、MIG、软件共享和自定义资源形态，也能够把配置好的资源名称写入容器的申请量和限制量。

接入时需要：

```text
HAMi 在真实 GPU 集群中运行
  → 向 Kubernetes 发布扩展资源
  → 平台资源池配置对应资源名称和资源形态
  → 平台盘点并选择本地候选
  → 运行计划写入资源申请
  → Kubernetes 和 HAMi 完成实际设备分配
```

这里必须区分三个层次：

1. 平台模型能够描述 HAMi 资源；
2. 平台能够读取和申请 HAMi 发布的 Kubernetes 资源；
3. HAMi 的显存、算力和设备隔离在真实硬件上生效。

前两项属于平台接入范围，第三项由 HAMi、驱动、设备插件和真实 GPU 环境实现并验收。平台不会自己创建 HAMi 虚拟设备，也不会仅靠资源字段实现 GPU 切分。

所以准确口径是：

> 平台在资源接口和控制流程上可以适配 HAMi，但真实共享、显存限制、算力限制和隔离效果仍需在 HAMi GPU 集群中验收。

## 6. 平台选择与 HAMi 调度会不会冲突？

平台和 HAMi 都包含“选择”动作，但理想情况下选择层次不同：

```text
平台
  → 决定 Local 或 Remote
  → 决定使用哪个本地资源池和资源形态

HAMi
  → 在选定的本地资源范围内
  → 决定具体节点、具体 GPU 和共享份额
```

未来接入可以考虑两种方式。

第一种方式是平台先选择节点，HAMi 再选择节点内的具体 GPU。这种方式接近当前平台的本地节点选择逻辑，但平台必须准确掌握 HAMi 的节点容量，避免两边判断不一致。

第二种方式是平台只选择 HAMi 资源池，把具体节点和设备交给 HAMi。这种方式解耦更强，更适合复杂共享调度，但平台的租约和最终绑定模型需要支持“创建租约时尚未确定具体节点”。

实际采用哪种方式，需要结合 HAMi 的资源上报、调度流程和平台租约语义，在真实环境中验证。

## 7. 当前没有本地 GPU，平台实验仍然证明了什么？

当前开发环境即使没有真实本地 GPU，仍然可以验证：

- Kubernetes 控制器和自定义资源；
- Local、Remote 和 Auto 选择；
- 本地资源申请与节点约束注入；
- 资源租约和容量核算；
- 排他远端入口占用；
- 控制器重复执行和恢复；
- 使用合成扩展资源模拟本地资源控制流程。

这些实验不能证明：

- 真实 GPU 能执行 CUDA；
- HAMi 显存和算力限制生效；
- 多任务共享具备实际隔离；
- 性能符合预期。

因此需要把“控制面契约通过”和“真实设备数据面通过”分开表述。

## 8. 本地 GPU 建议怎样逐步接入？

第一阶段先接普通整卡 GPU：

```text
NVIDIA 驱动和容器运行环境
  → NVIDIA 设备插件
  → 平台选择 Local
  → 容器看到真实 GPU
  → CUDA 结果校验
  → 租约释放
```

第二阶段再接 HAMi 共享 GPU：

```text
真实 GPU 和 HAMi
  → 共享资源上报
  → 平台选择 HAMi 资源池
  → HAMi 分配具体设备和份额
  → 验证显存、算力、共享和隔离
  → 核对平台容量与实际使用
```

第三阶段完成本地和远端统一选择：

```text
本地整卡 GPU
本地 HAMi 共享 GPU
远端 Cricket GPU
其他远端加速器
        ↓
平台统一盘点、选择和记录所有权
```

## 9. 现场可以使用的简短回答

如果被问到 Kubernetes 和 HAMi 的关系，可以回答：

> Kubernetes 是管理一组机器和容器任务的平台，负责把任务放到合适的机器上，并管理任务的启动、运行、失败和删除。HAMi 是建立在 Kubernetes 体系中的加速器管理中间件，补充 Kubernetes 对 GPU 和 NPU 的设备感知调度、共享、切分和隔离能力。

如果被问到我们的平台处于什么位置，可以回答：

> 我们的平台位于它们的上层，负责统一判断任务使用本地还是远端资源。如果选择本地，可以继续交给 Kubernetes 和 HAMi 完成具体节点与 GPU 分配；如果选择远端，则通过 Cricket 或其他远端适配器完成计算。
